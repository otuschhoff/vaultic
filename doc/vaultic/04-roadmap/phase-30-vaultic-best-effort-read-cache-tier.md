# Phase 30: Vaultic best-effort read-cache tier

[Back to roadmap index](00-overview.md)

[Previous: Phase 29](phase-29-slatedb-read-cache-tiers.md) | [Next: Phase 31](phase-31-read-only-nfsv3-snapshot-server.md)

**Status: design specification, not yet implemented.**

**Goal:** add a `read-cache` tier to Vaultic that retains frequently read repository data on local disk, S3-compatible storage, or native librados. Snapshot mounting is a primary workload: repeated browsing and random reads should reuse verified hot data without promoting the cache into authoritative storage.

## Scope and prerequisites

Reuse the placement/read-router abstractions, Phase 27 RADOS backend, and the cache policy/control-plane concepts from Phase 29. Keep Vaultic repository data caching separate from VaulticDB's SlateDB cache and from existing durable hot/cold placements. Preserve existing local cache and mount behavior when no new tier is configured.

## Design

### A disposable tier

Register `read-cache` as an explicitly non-authoritative role. Cache copies must not satisfy minimum replica counts, offsite/RPO requirements, journal durability, snapshot commit prerequisites, or prune reachability guarantees. Losing every cache must leave every committed snapshot recoverable from durable placements. Do not delete a durable copy merely because a cache copy exists.

Read in priority order from enabled cache targets, then use the existing authoritative placement router. Verify cache bytes against the repository's authenticated object/blob identity before returning them. Misses, corruption, quota exhaustion, cache permission failures, and target outages bypass to origin; only failure of all valid authoritative sources fails the read. Partial cache availability is expected: satisfy valid ranges from cache and fetch only missing or unavailable ranges from an authoritative placement when the representation permits independent range verification. A cache hit is not authorization: repository unlock and applicable leases must still be valid.

### Contents, identity, and security

Identify each cached representation by repository identity, authenticated source content, offset/length, format version, codec, and encryption context. Whole-file identities bind the ordered blob IDs, lengths, and sparse layout from authenticated snapshot metadata, not merely a path or timestamp. Each independently authenticated chunk becomes visible only after its successful fill and validation; container metadata records which chunks are complete. Never present an incomplete container as complete or satisfy a range with unverified bytes. Do not cache locks, mutable control state, or credential material as repository data.

Provide a per-target `trust=encrypted-only|plaintext-allowed` policy, defaulting to `encrypted-only`. The latter explicitly permits unencrypted objects, including compressed plaintext, blobs, chunks, and verbatim files, only on the named trusted target. It must require an authenticated operator decision and a recorded acknowledgement that anyone with storage access may read cached content without repository keys, even after broker lock. A local target, CephX access control, TLS, or provider-side disk encryption must not implicitly enable this mode. Transport protection and storage confidentiality are separate settings; retain authenticated encrypted transport for remote cache traffic.

With `encrypted-only`, retain repository ciphertext or wrap derived representations in a versioned, authenticated cache-encryption format whose keys follow the existing broker custody and lease rules. With `plaintext-allowed`, skip that encryption cost but never skip integrity verification. Validate source blobs before publishing derived entries; authenticate cache manifests and per-range cryptographic digests with a domain-separated repository-bound key so whole-file random reads can verify bounded ranges without rehashing entire files. A checksum stored beside data without authenticated provenance is insufficient. Verify the bytes actually returned, with immutable publication/version checks preventing verification/read races. Hashing and authentication overhead remains part of every performance comparison.

Trust changes apply online to new admissions and reads. Tightening to `encrypted-only` immediately stops plaintext use/fills, retires the plaintext namespace, and reports asynchronous purge progress and failures; re-encryption is optional only within budget. Do not claim secure erasure from SSDs, object versions, snapshots, replicas, or backups. Persistent plaintext cannot provide cryptographic revocation on lock; deployments requiring that property must reject plaintext mode. Clear process-owned plaintext buffers on shutdown where practical, but document that kernel/client page caches are outside this guarantee. Never migrate plaintext to a less-trusted target without encrypting it first.

Isolate cache prefixes/pools from origin and lease cache-only write/delete authority for fill and eviction. Read-only origin credentials must remain read-only even when the cache permits mutation. Apply broker-expiry and secret-hygiene rules to all cache transports, and report native/static credentials honestly. Vaultic still requires a valid unlock and applicable leases to serve any cached representation; this does not revoke direct storage access to previously persisted plaintext.

### Representation assessment

The following is a qualitative assessment, not measured throughput. Compare formats at the same backend, workload, trust policy, and byte budget. Here a blob is an existing repository content-defined chunk; a cache chunk is an independently verified range that may be smaller or coalesce several blobs. Verify the repository's actual per-blob compression/encryption boundaries before implementing transformations. A decrypted pack is a new indexed cache container, not a valid repository pack with an encryption flag removed.

| Representation | Read speed characteristics | Read-cache size usage | CPU usage | RAM usage |
|---|---|---|---|---|
| Original encrypted pack files or complete authenticated encrypted blob ranges | Avoids origin fetch; each hit still decrypts and decompresses; ranged lookup avoids unrelated payload reads | Preserves source compression and deduplication; whole packs retain cold neighbors, ranges need more index entries | Low fill cost; hit costs include decrypt, decompress, and verification | Bounded range/blob buffers plus decoder workspace; never load entire packs by default |
| Decrypted, still-compressed pack containers | Avoids decryption on trusted targets, but decompression remains; useful for warm data and fewer backend objects | Near compressed source size plus cache index/authentication metadata; whole-container eviction can retain unwanted blobs | Decrypt/verify once on fill; decompress and verify on hit; repacking costs CPU/I/O | Bounded compressed range and decoder buffers, plus pack index |
| Decrypted, decompressed pack containers | Fast indexed reads without codec work, but cold neighbors still consume space | Expanded payloads; generally worse useful-byte density than selected blobs; little benefit from original packing for sparse access | High initial decode work; low hit cost plus verification | Bounded read buffers possible; avoid whole-pack decoding/allocation |
| Individual compressed plaintext blobs | Good compromise for warm random access; many small remote requests can dominate | Compressed, deduplicated at blob granularity; per-object overhead and minimum allocation can be expensive | No hit decryption in trusted mode; decompression and verification remain | One blob/decoder workspace per active read plus bounded index |
| Individual decoded plaintext blobs | Fast reuse across files/snapshots without decrypt/decompress | Expands compressible data but preserves blob deduplication; small-object overhead remains | Decode once on fill; hashing/copying on hits | Bounded blob buffers; large blobs amplify small reads unless range integrity is available |
| Decoded fixed-size chunks or coalesced extents | Fine random access with tunable request size; excessive fragmentation increases remote latency | Retains only hot ranges; index/authentication overhead and lost cross-file deduplication may offset savings | Fill may decode whole source blobs; hit verifies selected chunks | Bounded chunk buffers, more metadata for small chunks |
| Whole verbatim unencrypted files | Usually best local repeated sequential/seek access; remote targets still pay network/range-request latency | Often largest footprint: decompressed and duplicates shared blobs across files/versions; preserve holes locally, use extent maps remotely | Assemble/decode/verify once; hits still verify ranges and copy bytes | Streaming construction and reads need not hold a whole file; OS page cache can dominate memory |

Derived formats may also be encrypted for untrusted targets, adding cryptographic CPU and framing overhead without requiring decompression if already decoded. Hardware-accelerated decryption can be cheaper than decompression or network I/O, so plaintext does not guarantee a meaningful speedup. Whole files are not universally best for sparse random workloads or slow remote caches. Baseline recommendation: encrypted source packs/ranges everywhere, compressed derived containers for warm trusted storage, and decoded blobs/extents or verbatim files only when observed reuse justifies expansion. Fully decompressed packs are a benchmark candidate, not a default.

### Native RADOS chunking and degraded reads

Treat a native librados replicated pool with `size=1` and `min_size=1` as a primary supported cache deployment. It deliberately provides no cache redundancy: an OSD or host outage can make the placement groups and cache objects mapped to it unavailable or permanently lose them. This is acceptable only because the cache remains disposable and at least one separately authoritative placement exists. Warn clearly if the selected authoritative fallback shares the same single failure domain, pool, or cluster such that the claimed fallback would fail with the cache.

Do not store a large logical cache representation as one indivisible RADOS object. Use a versioned chunked-container format with an initial configurable RADOS payload target of 4 MiB and a smaller final chunk. Treat 4 MiB as an implementation default to validate, not a universal Ceph guarantee: benchmark object-count/PG distribution, BlueStore allocation overhead, request and index amplification, sequential throughput, random-read amplification, and OSD memory/CPU before fixing supported bounds or changing the default. Expose the effective chunk size per target and include it in the immutable representation format; changing it creates a new cache generation rather than reinterpreting existing objects.

Chunking is a physical cache-storage layer distinct from repository content-defined blobs and Ceph/BlueStore's internal blobs. A repository blob smaller than the target may share a cache object with adjacent data only when each subrange remains independently authenticated and reclaimable accounting is correct. A blob, pack, decoded extent, or whole file larger than the target is split into approximately 4 MiB RADOS objects. For compressed derived data, use independently decodable frames instead of cutting an indivisible compression stream. For encrypted derived data, authenticate each chunk independently with representation identity, logical offset, length, and chunk ordinal as associated data. Original repository ciphertext may be physically split, but reads must collect the exact source ranges needed by the repository decrypt/authenticate boundary.

Derive chunk object names and fixed geometry from the authenticated representation identity where possible so an unavailable catalog or descriptor does not hide otherwise addressable chunks. Variable framing, sparse maps, and whole-file layouts use a small authenticated descriptor; cache its metadata locally, but treat descriptor loss or unavailability as a miss for the affected logical representation. Never guess boundaries from surviving objects. Publish chunks with create-only or version-checked writes; a descriptor may advertise only successfully published chunks, and an incomplete generation remains safely reusable at chunk granularity. Garbage collection recognizes unreferenced chunks and interrupted generations without requiring them for correctness.

For each requested range, resolve the minimum required chunk set and issue bounded parallel librados reads. A successful, authenticated chunk can be returned even when neighboring chunks or unrelated placement groups are unavailable. On `ENOENT`, unavailable/inactive/stale/unfound PGs, I/O errors, or a per-chunk cache deadline, mark only that chunk as a transient miss and fetch its exact logical range through the authoritative placement router. Do not wait for Ceph indefinitely in the hope that an OSD returns: use a shorter cache deadline than the end-to-end read deadline, cancel or detach the librados request safely, and preserve enough time for origin fallback. If the authoritative source lacks efficient range access, coalesce its fetch according to that source's normal read contract without treating cache chunk boundaries as repository format.

Assemble mixed-source results in logical order and verify every contributing range under the authenticated source identity before returning bytes. Never combine chunks from different generations, codecs, trust domains, files, or encryption contexts. If verification fails, discard that chunk and retry from an authoritative source. A failure is user-visible only when all authoritative routes needed for the requested range fail; cache-only errors remain metrics/events and may add bounded latency.

Keep a short-lived negative availability cache and per-target or placement-group circuit breaker so repeated reads do not hammer a down OSD or consume the entire request budget. Negative entries suppress cache probes, not authoritative reads, and expire or clear on fresh Ceph health/map evidence. Do not delete or permanently demote a chunk merely because it timed out; it may become readable when the OSD returns. After a successful origin fallback, refill the missing chunk only when admissions are enabled, the pool can accept writes, and retry backoff permits it. Coalesce concurrent repairs and use immutable publication so an old timed-out operation cannot overwrite a newer valid chunk.

A 4 MiB split reduces the failure and refetch amplification of a large cached file, but it does not guarantee adjacent chunks land on different OSDs or that any particular fraction survives: CRUSH maps each object independently through placement groups, and an unavailable PG can affect many chunks. Report available/unavailable chunk and logical-byte coverage rather than declaring an entire representation present from catalog metadata alone. Score and evict physical chunks with awareness of their logical representation; charge descriptor/index overhead and object-count quotas. Avoid deleting healthy chunks simply to make a partially unavailable representation look atomic.

### Mixed representations and value-based eviction

Support multiple representations concurrently under one budget, with a versioned representation catalog and per-target allowed-format policy. Require at least encrypted source packs/ranges, compressed derived containers, decoded blobs/extents, and whole-file materialization. Benchmark the remaining variants before enabling them by default. Select the cheapest valid hit using observed latency, decode work, tier priority, and current chunk availability, without probing every remote format serially. A partially available higher-value representation may satisfy its surviving ranges while lower representations or authoritative storage supply the rest.

Very hot, repeatedly accessed files can be materialized verbatim on plaintext-allowed targets. When reuse decays, evict that expanded copy while opportunistically retaining an already cached decrypted-but-compressed pack or blob representation. Do not recompress an old file just to manufacture a colder copy unless expected future benefit exceeds conversion and storage costs. Promotion/demotion is optional optimization, not a durability transition, and must not cause origin downloads simply to fill spare space.

Rank entries by marginal expected read benefit per reclaimable byte, not age alone. Use decayed frequency and recency, requested-byte coverage, measured latency saved versus the next retained representation/origin, CPU saved, operator/workload priority, and fetch/transform cost over a common prediction horizon. Normalize costs into documented comparable units; report score components. Account for overlap: a file and its blobs must not both receive credit for avoiding the same origin read. For packs, score the useful member blobs but charge the full physical container; shared chunks release bytes only when their last cache reference is removed.

Evict invalid, disallowed, and expired entries first, then the lowest marginal-value entries until the budget is satisfied. Use LRU as a tie-breaker and selectable baseline; retain idle/absolute ageing and scan-resistant admission. Admit a candidate only when its expected benefit exceeds the victims' lost benefit plus conversion cost. Priorities are weights, never permanent pins that override capacity. Bound scoring metadata, conversion workers, and hysteresis to avoid promotion/eviction churn.

### Mount and other read workflows

Integrate pack/blob caching at the shared repository read path and file/extent caching at a protocol-neutral file-read layer, so mount, restore, dump, and Phase 31 NFS snapshot serving reuse the same cache manager rather than protocol-specific implementations. Phase 31's `snapshotfs` extraction must preserve this integration. FUSE read-only mounts and NFS exports using the same cache identity share persistent entries, representation policies, capacity accounting, and eviction coordination, including across processes; process-local RAM caches have separate explicit bounds. Preserve seek/range semantics and coordinate concurrent misses for the same data. Allow bounded prefetch for sequential access; cancellation, scan-heavy workloads, and sparse/random reads must not trigger unbounded downloads or evict the entire useful working set.

Reusing cached data after mount restart is allowed only with correct repository and content identities. Origin retirement must not let a stale cache resurrect a deleted snapshot namespace. Define explicit offline use separately; normal cache fallback is not a promise that uncached snapshot data is available offline.

### Policy and operations

Provide per-tier and aggregate maximum size, value-based eviction/LRU, idle/absolute ageing, read/admission priorities, and online grow/shrink/drain behavior, using Phase 29 policy utilities where practical. Charge all retained representations, indexes, integrity metadata, staging, partial uploads, and conversion scratch against the budget; duplicate representations are not free. On disk charge allocated blocks including open-but-unlinked files, not apparent sparse-file length. On object stores track stored bytes and allocation overhead separately from estimated replicated/erasure-coded raw consumption. Bound RAM, page-cache pressure, request buffers, and conversion memory separately from persistent cache capacity.

Before filling or transforming, atomically reserve the worst-case added bytes across all participating processes, or evict first; stream or reject entries larger than the admissible budget. Never exceed a fixed admitted budget by hiding temporary copies outside it. When a requested limit drops below current usage, enter an explicit shrinking state: immediately stop excess admissions, cancel optional fills/conversions, retire victims, and report outstanding pinned or deletion-pending bytes. New requests cannot indefinitely renew pins on retiring entries; they bypass to another representation/origin. Complete the resize only after actual reclamation, with bounded reader drain deadlines and visible deletion failures. A smaller requested target cannot retroactively reclaim in-flight bytes, so report target versus actual usage honestly. Zero drains/disables; growth and priority changes take effect without unmounting or restarting.

Use one quota coordinator per shared cache domain, with fenced ownership and atomic reservations (or provably bounded partitioned grants), including multiple repositories and FUSE/NFS processes. Reconcile crash leftovers before reissuing capacity. Losing coordination disables new fills, not reads from origin. Persist authenticated policy revisions and offer status/update/drain operations with compare-and-swap updates.

### Ceph opportunistic capacity

Dynamic sizing is feasible with native librados, but not from a simple percentage of cluster-free bytes. [Librados usage statistics](https://docs.ceph.com/en/latest/rados/api/librados/) expose `rados_cluster_stat` (total/used/free raw device capacity, eventually consistent) and `rados_ioctx_pool_stat` (pool usage, not namespace-exclusive headroom). [Ceph capacity reporting](https://docs.ceph.com/en/latest/rados/operations/monitoring/) describes pool `MAX AVAIL` as an estimate dependent on replication/erasure coding, CRUSH placement, device utilization, and fullness settings. Obtain structured monitor/manager telemetry for pool quotas, `MAX AVAIL`, device classes, and relevant OSD fullness, using narrowly scoped read-only permissions. Validate APIs, units, and JSON schemas against supported Ceph releases; the linked latest documentation is a development reference.

Offer opt-in `budget-mode=fixed|ceph-free-space` with configurable reserve percentage (for example 10% of total raw cluster capacity), minimum free bytes, safety margin, maximum cache bytes, telemetry interval/max age, growth rate, and hysteresis. An explicitly selected auto ceiling may use all safely available headroom; zero still means disabled, not unlimited. Apply a reserve to the cache's eligible CRUSH/device-class capacity as well as the overall cluster. Unused HDD capacity cannot justify filling an SSD-only pool.

Compute a raw-space control target from a coherent observation, then separately enforce logical-byte and pool constraints:

```text
reserve_raw = max(reserve_fraction * total_raw, minimum_free_raw)
target_cache_raw = max(0, cache_raw + free_raw - reserve_raw - safety_margin_raw)
```

Here `cache_raw` is this coordinator's accounted footprint already included in cluster usage; adding it back avoids repeatedly shrinking a cache merely because its own fills reduced free space. Repeat the constraint for the eligible storage set and take the stricter target. Clamp by operator ceilings, remaining pool byte/object quotas, and safe pool `MAX AVAIL` headroom; never sum `MAX AVAIL` across pools sharing devices. Translate growth reservations with conservative upper bounds on raw amplification from replication/EC, allocation granularity, and metadata, without assuming compression savings. Reconcile actual usage and observe freed space after deletion rather than assuming the growth multiplier accurately predicts reclaimed bytes. Use a dedicated cache pool where practical; a shared pool requires namespace accounting and cannot attribute all pool usage to this cache.

For illustration only, with 100 TiB total raw, 20 TiB free, 30 TiB already used by this cache, and a 10 TiB reserve, the raw target is 40 TiB before extra safety/pool constraints. If other workloads then consume 15 TiB while cache usage is unchanged, the target falls to 25 TiB and at least 5 TiB of cache raw usage must be reclaimed. The target is not 40 TiB of logical cache objects on a replicated pool.

Poll off the read path and react to fresh pressure signals; grow slowly only above a higher resume watermark and shrink promptly below the reserve plus safety margin. Cache filling remains demand-driven. Stop admissions and prioritize eviction on relevant nearfull/backfillfull/full conditions, quota reductions, or topology changes even if aggregate free space appears sufficient. An OSD or host loss in an explicitly configured `size=1` cache pool stops fills and repairs to affected or unhealthy placement groups and activates degraded-read fallback, but does not require evicting healthy chunks or disabling authoritative reads. Ceph's stricter health thresholds override an operator's 10% example; never override fullness protections to write cache data. Multiple cache controllers sharing cluster headroom must use one cluster-level allocation authority or disjoint assigned budgets, not each claim the same free space.

On stale, denied, inconsistent, or unavailable telemetry, freeze growth immediately and shrink toward a configured conservative fallback (default zero after the telemetry deadline). Track outstanding reservations since each sample and include burst/recovery headroom; require several fresh stable samples before resuming growth. Keep eviction possible independently of a mount process's lifetime through the shared coordinator, with cache-delete-only authority. Cache pools must not retain snapshots, object versions, or other retention that prevents prompt reclamation; otherwise disable opportunistic mode or explicitly charge all retained versions with a verified reclaim mechanism.

This is best-effort reclamation, not a hard cluster free-space guarantee: external writers can consume space faster than statistics and deletes converge, and permissions/outages may prevent reclamation. Report reserve shortfall, telemetry age, and stalled eviction; never delete non-cache data or promise other workloads cannot encounter ENOSPC. Generic S3 has no portable cluster-capacity API; use fixed limits unless a separately configured trustworthy provider capacity adapter exists. Local disk may use filesystem-available-space signals with the same reservation and safety principles.

### Observability and benchmarking

Expose configured/effective trust and formats, requested/effective budgets, logical/allocated/raw-estimated bytes, staging/reservations/pins, occupancy by representation, hits/misses, bytes served, origin fetches, CPU/latency savings, eviction score/reason, promotion/demotion, corruption, resize progress, and per-workload effectiveness. For Ceph include effective chunk size, pool `size`/`min_size`, available/unavailable chunk and logical-byte coverage, cache-read deadlines, negative-cache/circuit-breaker state, fallback bytes/latency/reason, repair backlog, reserve/shortfall, pool/CRUSH constraints, sample age, fallback state, and actual reclaim lag. Configuration and authenticated operational commands must distinguish disposable cache eviction from destructive repository maintenance. Clearing a cache requires only cache authority, never repository-maintain authority.

Benchmark all candidate representations with equal budgets and integrity checks on local disk, S3, and librados: cold/warm sequential scans, repeated whole-file reads, sparse seeks, small random reads, shared blobs across snapshots, compressible/incompressible content, and mixed hot/cold working sets. For librados compare at least 1, 4, 8, and 16 MiB physical cache chunks, including `size=1` healthy and degraded operation, while respecting supported Ceph object and request limits. Measure throughput, p50/p95/p99 latency, useful bytes per allocated cache byte, origin traffic, request/object counts, unavailable-range fallback and read amplification, CPU time per GiB, peak RSS/decoder memory, page-cache effects, and conversion/eviction cost. Separate fill cost from steady-state hits and client/kernel cache hits from application-cache hits. Deliver measured recommendations and defaults; do not assert plaintext, mixed representations, or 4 MiB chunking outperform alternatives without evidence.

## Implementation steps

1. Add the non-authoritative `read-cache` role and prevent its use in durability, placement retention, or prune decisions.
2. Implement trust policy, authenticated representation identities, safe plaintext opt-in/revocation handling, and verified bounded fills for local disk, S3, and librados, including the versioned RADOS chunked-container format.
3. Deliver the mixed-representation catalog and required formats, promotion/demotion, value-based admission/eviction, LRU/ageing, and overlap-aware accounting.
4. Implement coordinated hard admission budgets, online resizing/priority updates, crash reconciliation, status, and safe clear/drain operations.
5. Add Ceph telemetry adapters, per-chunk deadlines/circuit breakers and authoritative fallback, and the opportunistic capacity controller with raw/logical accounting, reserves, health overrides, hysteresis, and conservative failure handling.
6. Wire FUSE read-only mount and other repository readers through the shared manager and file-read interface handed off to Phase 31, including coalescing and bounded prefetch.
7. Run the representation/workload benchmark matrix and document measured recommendations, trust tradeoffs, capacity-controller limitations, and cache-loss recovery.

## Tests

- Mount snapshots on cold and warm caches for every backend; verify byte-identical sequential/random reads, directory browsing, repeated opens, and concurrent readers.
- Exercise partial fills, cancellation, corrupt entries, repository/key isolation, pack changes, broker expiry, and total cache loss; valid origin reads must remain correct.
- In an isolated multi-OSD Ceph cluster, use a dedicated `size=1`, `min_size=1` cache pool, distribute a large representation across many 4 MiB cache objects, stop one OSD and then its host, and read ranges spanning available and unavailable chunks. Assert surviving chunks remain hits, only affected ranges fall back, output is byte-identical, latency is bounded, and no cache error escapes while authoritative storage is healthy. Repeat after OSD recovery and permanent chunk loss.
- Test unavailable/inactive/stale/unfound placement groups, blocked librados reads, `ENOENT`, I/O errors, lost descriptors, mixed-generation chunks, timeout races, late completions, and concurrent repair. Verify negative availability caching and circuit breakers prevent retry storms, origin fallback retains deadline budget, and refill never overwrites a valid generation.
- Test 4 MiB boundary reads, one-byte crossings, final short chunks, blobs/files/packs smaller and larger than a chunk, sparse files, independently framed compression, encrypted chunk associated data, partial publication, and interrupted garbage collection. Compare 1/4/8/16 MiB candidates and record object-count, space, CPU/RAM, request, latency, and degraded-refetch tradeoffs.
- Test mount-time grow/shrink, LRU and ageing eviction, priority changes, draining, restart reuse, quotas, and bounded prefetch under scan pressure.
- Test encrypted-only defaults, target-specific plaintext opt-in, compressed plaintext exposure, trust tightening/purge failure, and rejection of unauthenticated or tampered file/range manifests. Broker lock stops application reads without falsely claiming persisted plaintext becomes unreadable.
- Exercise hot-file promotion, cooling to retained compressed packs, shared blob references, overlap-aware victim scoring, and conversion failures. Assert total charged bytes plus reservations never exceed the admitted fixed budget, including staging and simultaneous processes; forced shrinking completes after bounded pins and confirmed deletes.
- Simulate Ceph external growth, freed space, cluster/CRUSH shrink, replicated/EC pools, small-object overhead, quotas, OSD imbalance, stale telemetry, denied stats/deletes, controller failover, and delayed reclamation. Verify no double allocation, conservative fallback, health overrides, automatic shrink/regrowth without oscillation, and alarms when reserve recovery is impossible.
- Run an isolated Ceph integration with a separate non-cache writer consuming/releasing space; observe reserve recovery and useful warm-cache retention within declared sampling/reclaim bounds. Test refusal of opportunistic mode with unreclaimable snapshots/versions.
- Run prune/GC, placement scheduling, and deferred publication with only cache copies present; caches must never authorize durable deletion or satisfy commit/RPO requirements.
- Measure hit rate, origin bytes avoided, and latency on repeated snapshot reads; verify no regressions when caches are disabled or unavailable.

## Exit criterion

Vaultic can serve mounted snapshot hot data through a best-effort `read-cache` tier on local disk, S3, or librados. Explicitly trusted targets support unencrypted objects with documented confidentiality consequences and mandatory integrity checks. Multiple representations coexist under coordinated byte budgets, measured value-based eviction, and online resizing; hot verbatim files and cooler compressed containers are demonstrated. A native librados `size=1` cache splits large representations into independently authenticated, approximately 4 MiB objects; an OSD or host outage preserves hits for available chunks and falls back only affected ranges to authoritative storage within bounded deadlines. The Ceph controller opportunistically uses safe spare capacity and yields it under external pressure with observable failure bounds. Benchmarks quantify read speed, space, CPU, RAM, chunk-size, and degraded-read tradeoffs. Phase 31 receives the same cache manager and file-read contract used by FUSE. Integrity, application authorization, and durable-placement rules remain unchanged, and deleting every cache affects performance only, not repository correctness or recoverability.
