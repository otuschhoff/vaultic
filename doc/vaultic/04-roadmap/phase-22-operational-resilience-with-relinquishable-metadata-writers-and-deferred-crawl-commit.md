# Phase 22: Operational resilience with relinquishable metadata writers and deferred crawl commit

[← Back to roadmap index](00-overview.md)

[← Phase 21](phase-21-crawl-optimization-with-cwalk-and-pathdiff.md)

**Goal:** keep backup data moving through transient metadata-writer contention, VaulticDB maintenance, and complete VaulticDB unavailability. Allow an idle or operator-directed `vaulticdb` instance to relinquish SlateDB writer ownership and remain available as a non-fencing reader, then reacquire writer ownership when required. Allow `vaultic` to discover and connect to multiple data-pack backends before contacting VaulticDB, then crawl, encrypt, upload, and verify data packs when VaulticDB is read-only, unavailable, or corrupt by publishing a self-contained authenticated staging journal to those backends and committing its metadata later. Clearly distinguish durable staged data from a completed, normally restorable backup; never weaken single-writer fencing, snapshot publication ordering, quorum placement, or deletion safety to improve availability.

**Design:**

VaulticDB has an explicit lifecycle state machine: `read-only`, `promoting`, `read-write`, `demoting`, and `fenced`. Read-only instances use SlateDB `DbReader` in a non-fencing mode that follows the latest manifest and WAL without creating managed checkpoints; `SkipWalReplay` is prohibited where current metadata is required. At most one instance owns a writable `Db` for a repository and metadata endpoint. Opening or promoting a writer must acquire a fresh SlateDB fencing epoch through one authoritative strongly consistent coordination/object-store path; metadata replication may copy fenced results but must never elect independent writers from different replicas during a partition. A fenced instance rejects every new mutation, aborts or reports ambiguous in-flight operations without replaying them blindly, closes its writer, and reopens as a reader only after observing the winning epoch.

Automatic demotion is optional and disabled by default. In HA mode, a configurable idle grace period and minimum writer tenure prevent role thrashing; an authenticated administrative command can request immediate demotion. Client connection count alone never proves idleness. Before relinquishing ownership, VaulticDB enters `demoting`, rejects new transactions and write batches with a retryable role-transition response, waits for admitted write RPCs and durable acknowledgements, resolves or expires every transaction, stops metadata maintenance that may write, flushes and durably closes the writable `Db`, and only then reports `read-only`. Timeout or close failure leaves the instance non-promotable and fails closed rather than advertising that ownership was released. Promotion serializes concurrent requests, obtains a new fencing epoch, reopens the latest writable state, validates repository/schema/encryption generations, and requires each caller to revalidate its write intent. Requests carry durable idempotency keys; an ambiguous result is queried by key before retry and is never assumed absent.

Pack-backend bootstrap is independent of SlateDB. An operator supplies one or more seed locations through a local deployment profile/TOML file, repository file, CLI, or environment; the seed list contains repository locators and expected repository identity, never embedded credentials. After the Phase 20 broker grants the required repository capability, Vaultic reads the ordinary encrypted repository `config` object when available and a separately versioned bootstrap-topology manifest mirrored at deterministic paths on every designated bootstrap/staging backend. The manifest contains repository UUID, generation, backend IDs and locations, roles, `ingest`/`read_enabled` state, failure domains, staging eligibility, placement policy, and the hash of the corresponding repository configuration, but no passwords, tokens, cloud keys, or connection-string secrets. Backend credentials continue to come from workload identity, OS/cloud credential providers, protected local files, or approved secret stores.

The bootstrap-topology manifest is the metadata-outage authority for opening pack backends, not a second mutable copy accepted without reconciliation. Each generation is immutable, encrypted where endpoint confidentiality is required, and authenticated under a topology-specific key/capability separated from pack encryption and journal sealing. Topology mutation requires an authorized administrative broker capability, publishes and verifies the new generation to the required bootstrap mirrors before activation, updates the encrypted repository config projection when available, and records an externally auditable generation/hash anchor. Startup compares every reachable copy, the locally cached last-seen generation, repository config, and external anchor; it rejects same-generation conflicts, repository-ID mismatch, invalid authentication, and rollback below a trusted anchor. If repository config and SlateDB are unavailable, a valid non-rolled-back manifest from any configured seed is sufficient to discover and open all declared pack/staging backends. Total loss of all seed locators and all topology-manifest copies remains a documented bootstrap disaster requiring a protected offline manifest export.

Repository opening is reordered accordingly: resolve seed locations → contact/unlock the local broker → authenticate the latest bootstrap topology or decrypt the repository config → validate repository identity and placement policy → open all reachable eligible pack/staging backends → evaluate whether the required $K$-of-$M$ durability predicate can be met → only then attempt VaulticDB and select `read-write`, `read-only-assisted`, or `data-plane-only`. Failure to open one backend is reported per backend and does not abort staging when the remaining independent backends still satisfy policy. Vaultic must not silently weaken `min_copies`, `min_domains`, `min_offsite`, ingest state, or staging-journal durability because VaulticDB or a backend is unavailable.

Vaultic crawl supports three progressively degraded modes. In `read-write` mode it follows the normal transactional metadata and snapshot publication path. In `read-only-assisted` mode it may use a refreshing reader for prior-snapshot lookup and best-effort deduplication, but treats all observations as stale hints and uploads harmless duplicate blobs rather than relying on freshness. In `data-plane-only` mode it does not open or trust VaulticDB at all, including when metadata is absent, fails authentication, or is operationally unreachable; it performs a full source crawl unless an independent, fully verified `pathdiff` coverage proof safely narrows the scan, builds and encrypts packs locally, and interacts only with configured data-pack backends plus the local Phase 20 key broker. A corrupt VaulticDB is never repaired, overwritten, or used as a basis implicitly by a staging crawl.

Deferred crawls publish an immutable, versioned ingest journal under a repository-scoped staging namespace that compatible Restic/Rustic clients ignore. The journal is independently usable without SlateDB and contains all information needed for deterministic later commit: repository UUID; format, capsule/key, chunker, compression, and placement-policy versions; random job and idempotency IDs; crawl source identity and consistency evidence; the observed basis snapshot and metadata generation when available; encrypted pack IDs, types, sizes, blob IDs, offsets, lengths, compression metadata, and verified backend placements; tree and prospective snapshot records; required inode/path revisions and crawl debt; and hashes linking ordered journal segments to one final seal record. Journal objects are encrypted and authenticated with a purpose-separated staging key derived through the repository key hierarchy, bind every segment to repository/job/sequence/version, and are written with create-only semantics. No plaintext path, file metadata, pack key, share, or broker secret is exposed by staging objects or logs.

Pack upload and journal publication use an explicit state machine: `uploading` → `sealed-pending` → `committing` → `committed`, with `abandoned` and `expired` terminal cleanup paths. A journal becomes `sealed-pending` only after every referenced pack satisfies the configured $K$-of-$M$ durability and failure-domain predicate, each object has been size/hash verified, all immutable journal segments are durable on the required staging backends, and a final authenticated seal commits their ordered hashes. Incomplete or unsealed journals convey no backup durability guarantee and protect no packs indefinitely. A sealed journal is a temporary GC reachability root until its authenticated expiry, successful commit, or explicit abandonment followed by a safety delay and authoritative recheck.

The CLI and API report staged durability separately from repository commitment. A crawl may return a distinct successful-but-pending result such as `data_durable_metadata_pending`, including job ID, protected bytes, placement result, expiry, and why metadata was deferred. It must not publish the normal snapshot object, emit an ordinary backup-success notification, advance an incremental basis, satisfy a backup-completion SLO, or claim normal restorability before metadata reconciliation commits. An emergency restore tool may consume a sealed journal directly after authenticating it and verifying packs, but this is an explicit degraded recovery path and does not turn the journal into an authoritative snapshot prematurely.

When a writer becomes available, recovery always attempts **Plan A: deferred-journal reconciliation into the existing healthy generation** first. The reconciler discovers sealed journals from all staging backends, authenticates and de-duplicates them by repository/job ID, verifies the complete segment chain and seal, rechecks required pack placements and hashes, and rereads current metadata. It resolves concurrent blob locations additively, derives reference counts and mutable aggregates from current authoritative state rather than trusting stale precomputed values, applies deterministic creation/basis conflict rules, and commits packs, placements, blobs, trees, inode/path revisions, crawl debt, analytics inputs, and snapshot authority in one idempotent logical operation. The normal snapshot is published only after all referenced packs and authoritative metadata are durable. An immutable completion record binds the journal hash to the committed metadata transaction and snapshot ID; a crash after database commit but before completion publication is recovered by querying the idempotency ID, not by duplicating changes. Journals whose source-consistency or basis contract cannot be reconciled remain pending or are explicitly rejected, never silently rebased.

Plan A distinguishes retryable operational failures from evidence that the database cannot safely accept reconciliation. Writer contention, fencing transition, rate limiting, transient object-store errors, or broker lease interruption leave the journal pending and retry with bounded backoff; they never trigger an automatic rebuild. Authentication failure, malformed or missing manifests/WAL/SSTs, trusted-generation rollback, unrecoverable transaction/idempotency state, repository/schema identity mismatch, or a failed full integrity preflight marks the metadata generation `healing-required`, disables mutation and destructive operations, and produces a signed diagnostic report. Operators may keep serving reads only if their consistency level is proven; otherwise the generation is quarantined. No failure path repairs objects in place, overwrites the suspect generation, marks a journal committed, or silently invokes Plan B.

**Plan B: quarantined metadata rebuild** is explicit, resumable, and operator-authorized. `vaultic index heal plan` inventories the suspect metadata generation, capsule/topology anchors, legacy indexes and snapshots, all pack backends and placements, sealed and completed ingest journals, and any surviving authenticated metadata objects; it records usable reconstruction sources, irrecoverable fields, required crawl debt, estimated work, and the target DEK/generation without changing authority. `vaultic index heal execute --plan <id>` writes a new isolated SlateDB namespace and generation, using the recovered metadata DEK only when policy permits or a fresh metadata DEK published through a new Phase 20 capsule generation before the first write. The old namespace remains immutable and addressable for forensic analysis and rollback until explicit retirement.

Rebuild establishes a conservative baseline from authenticated sources in authority order: accepted completion records and surviving metadata transactions where independently verifiable; legacy Restic/Rustic indexes, snapshots, trees, and pack headers/listings; verified per-backend pack placements; then sealed pending journals replayed idempotently in deterministic order. It reconstructs pack/blob locations and immutable snapshot/tree facts, recomputes reference counts, reverse indexes, placement summaries, and other mutable aggregates, and records inode/path history, analytics, timestamps, and classifications that cannot be proven as explicit crawl debt or unknown values rather than inventing them. Conflicting authenticated sources stop the affected item or entire rebuild according to a documented severity policy and require operator resolution; source priority never hides a cryptographic or repository-identity conflict.

The rebuilt generation passes staged activation gates before it can become authoritative: capsule/topology/repository identity and anti-rollback validation; full SlateDB structural and AEAD verification; pack, blob-offset, tree, snapshot-root, placement, failure-domain, and journal-completion consistency checks; comparison against every available legacy projection and source inventory; zero unresolved critical conflicts; and a signed healing report containing source coverage, omissions, crawl debt, journal outcomes, and object counts. It is first opened read-only for inspection. Activation requires explicit approval, an authoritative generation compare-and-swap, publication and mirroring of the new generation anchor, client re-resolution, and only then acquisition of a fresh writer fencing epoch. Failure or crash before that atomic activation leaves the prior authority unchanged and the candidate resumable or disposable. Destructive maintenance stays disabled until a post-activation `index check` succeeds and a configurable observation window expires; retiring the quarantined generation is a separate high-severity audited operation.

Prune, GC, placement eviction, and orphan cleanup enumerate sealed unexpired staging journals before making deletion decisions. They must not delete a referenced staged pack, must not count staged references as committed repository references, and must recheck both journal state and authoritative metadata immediately before deletion. Expiry does not directly delete data: it makes a journal eligible for an audited abandonment flow followed by a configurable grace period, placement revalidation, and idempotency lookup. Staging quotas bound bytes, jobs, age, and per-principal concurrency so an unavailable metadata plane cannot exhaust the data backends; crossing a hard quota stops new uploads before durability is claimed. Administrators can inspect, reconcile, extend within policy, abandon, and garbage-collect jobs, with high-severity acknowledgement for abandoning a sealed journal.

The Phase 20 broker grants a transient crawl only the repository-key capability needed to encrypt packs and derive the purpose-separated staging-journal key. Read-only VaulticDB instances obtain only metadata-DEK leases. Writer role transitions do not require a new quorum while the local broker unlock epoch remains active, but another host needs its own authorized and unlocked broker; this phase does not introduce remote key release. Data-plane-only mode therefore tolerates total VaulticDB loss but not loss of every capsule, an unavailable locked broker, unavailable pack backends, or failure to meet the configured placement quorum.

**Implementation steps:**

1. Add a versioned VaulticDB role API and observable state machine for `read-only`, `promoting`, `read-write`, `demoting`, and `fenced`, reporting instance ID, current and observed writer epochs, transition reason/time, active write intents, transaction count, last durable sequence, idle deadline, and whether promotion is currently safe.
2. Refactor VaulticDB storage ownership so it can close and replace a writable `Db` with a non-fencing `DbReader`, and later replace the reader with a freshly fenced writable `Db`, without restarting the service or dropping its broker lease. Use `FollowLatest` with WAL replay for current reads, bounded manifest polling, refresh-and-retry on stale-object misses, and GC retention exceeding maximum supported reader staleness.
3. Implement the demotion quiescence barrier: write admission gate, tracked RPC/write/maintenance intents, transaction drain or expiry, durable-ack drain, engine flush/close, timeout handling, and fail-closed state publication. Add `VAULTICDB_WRITER_IDLE_GRACE`, minimum-writer-tenure and transition-timeout settings plus `vaultic index writer status|promote|demote`; keep automatic demotion opt-in.
4. Implement promotion and fencing against one authoritative strongly consistent path using SlateDB's manifest/WAL fencing and backend conditional operations. Serialize promotion, reject stale epochs, validate repository/schema/encryption generation after reopen, expose retryable `not-writer`, `promoting`, `demoting`, and `fenced` errors, and require idempotency lookup for ambiguous writes. Prohibit promotion through a lagging metadata replica or independent per-replica election.
5. Define the immutable bootstrap-topology manifest, deterministic mirror paths, protected offline export, seed-locator profile/TOML format, topology-specific broker capabilities, generation/hash anchors, and reconciliation rules with the encrypted repository config. Refactor repository opening to authenticate topology and attach multiple placement backends before VaulticDB resolution; resolve credentials only through approved runtime providers, report partial connection failures, and continue only when reachable ingest/staging backends satisfy the unchanged durability policy.
6. Define a canonical versioned ingest-journal schema and staging namespace with segmented bounded-size records, ordered hash chaining, final seals, completion/abandonment records, repository/job/idempotency binding, purpose-separated authenticated encryption, create-only publication, backend compatibility rules, and forward-compatible discovery. Specify enough source, tree, pack/blob, placement, inode/path, debt, analytics, and prospective snapshot information to reconcile without recrawling or consulting the original VaulticDB.
7. Refactor crawl output behind a sink that supports normal transactional commit or deferred journal staging. Implement explicit `--allow-deferred-commit` policy with `auto`, `read-only-assisted`, and `data-plane-only` controls; entering data-plane-only mode after corruption requires explicit acknowledgement, emits a critical event, discards all metadata-derived optimization state, and selects a full crawl unless independent event coverage is proven.
8. Upload immutable packs concurrently to placement-selected backends, verify $K$-of-$M$ copies and failure domains, record per-object results in journal segments, and publish the final seal only after all pack and journal durability requirements pass. On interruption, preserve diagnosable incomplete state but never return the pending-success status or create a GC root without a valid seal.
9. Implement journal discovery, inspection, emergency direct restore, idempotent reconciliation, rejection, expiry extension, abandonment, and cleanup commands. Reconciliation is always Plan A: run an integrity and identity preflight, revalidate current metadata and physical placements, resolve additive duplicates, compute mutable records afresh, commit one logical transaction, publish the normal snapshot last, and write a completion record recoverably. Classify failures as retryable, journal-specific rejection, or `healing-required`; only the last class blocks database mutation and offers Plan B, and never starts it automatically.
10. Integrate sealed-journal roots and states into prune, GC, placement eviction, orphan detection, capacity planning, and checks. Add quotas and backpressure for staged bytes/jobs/age/principals, an abandonment safety delay, immediate pre-delete revalidation, and findings for missing packs, under-replicated journals, conflicting seals, expired jobs, stuck reconciliation, and completion/database disagreement.
11. Add stable human and JSON status plus `auth`, `integrity`, and `lifecycle` events for topology discovery/authentication/rollback, backend connection and policy sufficiency, writer transitions and fencing, deferred-mode selection, database corruption bypass, pack durability, journal seal/discovery/reconciliation/expiry/abandonment, emergency restore, quota refusal, and cleanup. Never log journal plaintext, backend credentials, paths, keys, shares, or secret-bearing broker data.
12. Implement `vaultic index heal status|plan|execute|verify|activate|rollback|retire` with stable machine-readable plans and reports. Keep suspect and candidate generations in separate namespaces; inventory and authenticate reconstruction sources; support resumable checkpoints; rebuild immutable facts conservatively; recompute mutable/derived state; preserve unknown facts as crawl debt; replay sealed journals idempotently; validate all activation gates; activate with an authoritative generation compare-and-swap and fresh writer fence; and require separate acknowledgement before rollback or retirement. `rollback` is allowed only before destructive maintenance resumes and must itself publish a newer authenticated authority decision rather than serving an old generation silently.
13. Add healing safety controls: mutation and destructive-operation interlocks for `healing-required`, `rebuilding`, `validating`, and post-activation observation states; immutable forensic retention of the suspect namespace; conflict-resolution records; fresh-DEK capsule publication before candidate writes where required; externally mirrored generation anchors; client generation re-resolution; signed healing reports; bounded candidate storage and cleanup; and audit events for every plan, source exclusion, conflict override, activation, rollback, and retirement.
14. Document seed and credential configuration, topology-manifest publication/recovery, normal, read-only-assisted, and data-plane-only guarantees; the difference between durable staging and committed backup; writer demotion/promotion operations; expected client retry behavior; broker and fencing prerequisites; Plan A retry/reconciliation behavior; Plan B trigger classification, planning, quarantine, reconstruction-source authority, DEK choice, validation, activation, rollback, and retirement; staged-job monitoring, quotas, expiry, emergency restore, abandonment, and disaster exercises. State explicitly that successful staging improves the recovery point but does not provide normal snapshot visibility or completion semantics until reconciliation or an approved rebuild succeeds.

**Tests:** VaulticDB role-state unit tests and multi-process integration tests for idle and manual demotion, minimum tenure, transaction/write/maintenance quiescence, durable close, demotion timeout, simultaneous promotion, stale epoch rejection, old-writer fencing, partitioned coordination, read refresh, reader GC races, repeated RW↔RO cycling, broker lease continuity, and crash at every transition boundary; tests proving no instance advertises read-only before writer close or read-write before fencing and generation validation; idempotency and ambiguous-commit tests proving no duplicated or lost transaction. Bootstrap tests cover config/profile/TOML and multiple seed locators; discovery from each individual mirror with repository config and VaulticDB absent; automatic connection to multiple pack backends before metadata resolution; runtime credential-provider isolation; one or more unreachable backends with policy still satisfiable; refusal when copies/domains/offsite requirements cannot be met; immutable generation publication crashes; config/manifest drift; same-generation conflict; foreign-repository, malformed, unauthenticated, rolled-back, and missing topology manifests; trusted local/external generation anchors; topology key separation; protected offline export; and total loss of the former primary backend. Deferred-crawl tests cover healthy RW, stale RO-assisted, unavailable, authentication-failing, and physically destroyed VaulticDB; full and independently verified `pathdiff` crawls; concurrent staged jobs; overlapping blobs; duplicate packs; every interruption before and after pack upload, segment publication, seal, metadata commit, snapshot publication, and completion record; $K$-of-$M$ partial failure and recovery; corrupt, truncated, reordered, mixed-job, replayed, foreign-repository, stale-key, conflicting-seal, forged-completion, expired, and oversized journals; reconciliation against metadata changed by other crawls; deterministic basis rejection; emergency restore; no-plaintext inspection; quota/backpressure; and compatibility with ordinary Restic/Rustic readers. Healing tests prove Plan A is always attempted before Plan B is offered; transient contention, fencing, provider, and broker failures remain retryable without rebuild; corruption, identity, rollback, and failed-preflight cases enter `healing-required`; and no fallback starts without an explicit plan and approval. Rebuild tests cover partial corruption and total metadata loss; recovered-DEK and fresh-DEK paths; every reconstruction source alone and in combination; conflicting source authority; unknown-fact crawl debt; exactly-once idempotent journal replay into the candidate; resumable checkpoints; separate namespaces; immutable suspect data; full validation gates; read-only candidate inspection; compare-and-swap activation races; client generation switching; fresh writer fencing; and crashes before and after candidate creation, anchor publication, activation, completion marking, rollback, and retirement. Destructive-operation race and chaos tests prove sealed journals protect staged packs, unsealed uploads eventually become collectible, completion removes temporary roots without exposing committed packs, abandonment/expiry can never delete a concurrently committed object, and no destructive maintenance runs during healing or the post-activation observation window. End-to-end disaster tests start with no readable repository config or SlateDB objects, discover topology from a surviving seed mirror, connect to enough independent pack backends, stage a crawl using only the broker and data backends, attempt Plan A, produce a signed healing diagnosis, execute Plan B into a fresh generation, replay the sealed journal into that candidate without recrawling or re-uploading, verify and atomically activate it, publish the completion record, restore the resulting snapshot, pass `index check`, and only then enable destructive maintenance.

**Exit criterion:** an authorized VaulticDB instance can relinquish writer ownership automatically after a configured grace period or manually, remain a refreshing non-fencing reader, and safely reacquire a newly fenced writer epoch without service restart, split brain, lost durable writes, or blind replay. From any surviving configured seed or protected offline export, Vaultic can authenticate a non-rolled-back topology, discover and connect to multiple eligible data-pack backends, and evaluate the unchanged placement policy before contacting VaulticDB; no backend credential is stored in the topology manifest. A Vaultic crawl can continue in explicitly enabled degraded mode when VaulticDB is read-only and can stage solely against pack storage when the repository config and VaulticDB are entirely unavailable or corrupt, provided the broker is unlocked and enough independent pack/staging backends remain reachable. Every pending-success result proves the journal and all referenced packs satisfy the configured durability predicate, but is visibly not a committed backup. Recovery always attempts idempotent Plan A reconciliation into a healthy writer first; retryable failures remain pending, while proven metadata damage fails closed as `healing-required`. If Plan A cannot safely proceed, documented tooling can inventory and quarantine the suspect generation, build and validate a separate conservative metadata generation from authenticated repository and journal sources, replay each sealed journal idempotently into that candidate, expose it read-only, and atomically activate it under a trusted generation anchor and fresh writer fence without modifying the suspect database. Activation never invents unavailable facts, starts automatically, or enables destructive maintenance before post-activation verification. The activated generation exposes exactly one normal snapshot per accepted journal without recrawl or re-upload and recovers correctly across every boundary. Sealed journals are temporary protected roots with bounded quotas and audited expiry/abandonment, while prune and GC cannot delete staged or concurrently committed data. Operators can observe and exercise writer transfer, primary-backend and metadata outage staging, topology recovery, Plan A reconciliation, Plan B healing, activation/rollback, direct emergency restore, and cleanup from documented commands, and a total metadata-loss exercise ends with a normally restorable, internally consistent repository.
