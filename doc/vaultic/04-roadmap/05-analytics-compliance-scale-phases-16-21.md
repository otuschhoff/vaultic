### Phase 16: Growth, churn, per-user/group attribution, and GDPR audit CLI

**Goal:** expose growth/churn and GDPR views plus exact, high-dimensional file
creation and live-versus-archive residency analytics across ownership, time,
source topology, custom path groups, and file size. Keep common queries fast
without precomputing every possible aggregate tuple.

**Implementation steps:**

1. Define versioned analytics configuration for source-root/LIF topology mapping,
  default SVM/volume extraction, custom `first-subdir`/depth/prefix path groups,
  history retention, query concurrency, and memory/persistent cache budgets.
2. Add dictionary-coded `af:` columnar creation segments, `am:` segment
  metadata, `ai:` compressed dimension bitmaps, and the mutable `ar:` residency
  overlay. Record UID, GID, exact logical size, decimal magnitude bucket,
  trustworthy birth time or first-seen basis, calendar year, ISO week-year/workweek,
  SVM, volume, custom group, and identity generation.
3. Emit creation facts only for new verified file identities. Update source
  state only after complete deletion proofs and update retained-snapshot
  reachability in snapshot publish/forget transactions. Atomically append
  idempotent `ae:` deltas with authoritative changes, consume them in commit
  order, and advance `aw:` only after a whole analytics commit is durable.
  Preserve `unknown` for incomplete evidence and expose metadata-head lag.
4. Implement a vectorized query engine that prunes segments, intersects bitmap
  predicates, applies exact range checks, joins residency, and computes count
  and logical-byte metrics for arbitrary filters/groupings. Add bounded
  concurrency, progress, cancellation, explain plans, snapshot consistency,
  and checkpointed asynchronous query jobs.
5. Add canonical query hashing, bounded in-memory and persistent result caches,
  scan-cost/frequency telemetry, watermark/epoch invalidation, TinyLFU-style

6. Implement `g:time:*`, `g:path:*`, `u:summary:*`, `g:summary:*`, and
  `u:churn:*` as rebuildable common materialized views. Implement `u:inodes:*`
  and `u:blobs:*` for exact GDPR lookup during reconciliation and snapshot
  purge transactions.
7. Implement `vaultic index analytics` with all ownership, creation-time,
  topology, custom-path, size, and residency predicates; arbitrary grouping;
  async query lifecycle; cache controls; `--explain`; and stable JSON.
8. Implement `vaultic index growth`, `index user-stats`, and
  `index gdpr audit --uid` on the same facts/views, including active/archive-only
  paths, blob hashes, pack locations, and retention expiry dates.
9. Add checkpointed `index analytics rebuild`, cache/view inspection and purge,
  classification-rule migration, and `index check` validation for fact/index,
  residency, dictionary, rollup, and adaptive-view consistency.
10. Benchmark 10M and 100M representative facts and extrapolate to 1.4B before
   general enablement. Measure compressed bytes/fact, write amplification,
   reconciliation overhead, bitmap cardinality, cold/cached latency, cache hit
  ratio, outbox catch-up lag, and rebuild duration. Any failed storage,
  overhead, lag, or query-timeout gate blocks general enablement and requires
  redesign plus a complete benchmark rerun.

week boundary and zero/unknown/decimal/exact-size tests; trusted birth-time,
clock-skew fallback, concurrent basis selection, and source-generation tests;

Failure of any gate leaves analytics experimental and off by default. Disabling

The numeric gates above are evaluated exactly by the [analytics feasibility](../02-architecture/07-analytics-engine.md) reference
profile: 1,000/1,000 brute-force comparisons match, the named broad query meets

Post-commit derived writes are measured separately; physical SlateDB compaction

**Current implementation state (2026-08-30): complete.** Analytics is optional,
disabled until explicitly enabled, purgeable, and fully rebuildable from the
authoritative index. Rebuild streams authoritative source keys into bounded,
zstd-compressed columnar `af:` segments; dictionary records, segment metadata,
per-value bitmap indexes, residency overlays, common rollups, ownership
summaries, churn views, and GDPR inode/blob mappings are all derived state.
Candidate generations remain invisible until a constant-size transaction
publishes their manifest, completion marker, watermark, and active metadata.
Checkpoint validation prevents a corrupt or stale rebuild cursor from skipping
facts.

Authoritative inode, snapshot-membership, and proven source-state changes append
ordered `ae:` deltas in the same serializable transaction as the source change.
Retained-reference deltas carry explicit increment/decrement semantics while
remaining compatible with the original encoded form. Bounded catch-up creates
parent-linked immutable generations without rescanning the inode namespace,
uses tombstones for replaced derived records, compacts at eight layers, and
reclaims outbox records only after durable watermark publication. Complete,
debt-free crawl proofs are the only evidence that can turn absence into
deletion; incomplete or scoped-out evidence remains `unknown`. Snapshot forget
changes logical retained-reference state independently of physical GC.

The query engine pins a complete manifest/watermark, prunes segments, intersects
zstd or raw bitmap indexes, applies exact range predicates, joins residency,
and supports arbitrary filter/grouping subsets. Missing or malformed optional
indexes fall back to exact scans and appear in explain output. Persistent jobs
checkpoint at segment boundaries and support start, resume, wait, cancellation,
and generation-safe cleanup. Generation-scoped result caches and bounded
adaptive `aq:view:` cuboids use canonical predicates, TTL and admission/eviction
budgets, and exact rollup compatibility checks.

`vaultic index analytics`, `growth`, `user-stats`, and `gdpr audit` expose the
facts and materialized views with stable JSON, explicit stale/current behavior,
cache/view/job inspection, and bounded catch-up controls. `vaultic index check`
exactly validates active manifests, parent chains, segments, dictionaries,
indexes, overlays, rollups, ownership/churn/GDPR views, outbox ordering, cached
results, adaptive cuboids, and pinned jobs.

**Verification performed:** deterministic query tests compare 1,000 arbitrary
queries with an independent brute-force oracle; crash tests cover candidate
writes, checkpoints, pointer publication, outbox replay, and job resume; tests
cover identity reuse, complete/incomplete crawl evidence, snapshot publish and
forget, archive-only/expired transitions, malformed-index fallback, cuboid

generation compaction, and concurrent rebuild/query/catch-up. Focused package
tests and analytics/index race tests pass. Exact 10M and 100M profiles and the

recorded write gate measures same-transaction encoded authoritative metadata;

### Phase 18: SlateDB metadata encryption and unified key envelope

**Goal:** encrypt every `vaulticdb` SlateDB object (SSTs, WALs, manifests, checkpoints) client-side at the `ObjectStore` boundary with a per-repository metadata key, manage that key through a versioned multi-slot envelope wrapping it independently in Azure Key Vault / AWS KMS / Google Cloud KMS and an offline local recovery key, and optionally hold the repository data master key inside the encrypted database with cloud-vault escrow so a single startup unlock opens both the metadata database and the restic-format data repository.

**Design:**

The metadata data-encryption key (DEK) is a random 256-bit AES key generated once per repository and distinct from the repository pack master key, the keyfile password, and every Phase 17 key: metadata and payload must have separate compromise boundaries, IAM permissions, and rotation schedules. The DEK is never persisted in plaintext. It is unwrapped exactly once at daemon startup and held only in daemon memory (best-effort `mlock`, core dumps disabled), so a temporary key-provider outage never interrupts a running daemon.

The DEK is stored in a versioned key envelope holding one wrapped copy per configured key-encryption-key (KEK) slot. Cloud slots use non-exportable keys through wrap/unwrap-style operations only — Azure Key Vault or Managed HSM `wrapKey`/`unwrapKey`, AWS KMS `Encrypt`/`Decrypt` with an encryption context binding the repository UUID and purpose, Google Cloud KMS `encrypt`/`decrypt`, and HashiCorp Vault Transit or PKCS#11 for self-hosted deployments. The offline recovery slot wraps the same DEK under an Argon2id-derived KEK from an operator passphrase (random salt and calibrated cost parameters stored in the envelope) or under an OS-keystore/TPM/PKCS#11-held key. Any single slot suffices to unlock, so a repository can be initialized and used with only the local recovery slot while cloud vault provisioning is still in progress, and cloud slots can be added later by rewrapping without touching any data. Slot use is policy-ordered: unlocking through the recovery slot while a higher-priority cloud slot is configured requires an explicit operator acknowledgement and emits a high-severity `auth` event, so a provider outage can never silently downgrade key handling. Envelopes are published as new versions beside the database and mirrored into the repository backend; the only decryptable envelope is never overwritten in place.

Encryption happens below SlateDB in an `EncryptedObjectStore` wrapper rather than per schema value, because value-level encryption would still leak key prefixes, paths, record distribution, WAL structure, and manifest contents. Each object carries an authenticated header (magic, format version, algorithm, DEK version, random object nonce, chunk size, plaintext length) and a body of independently authenticated AES-256-GCM chunks (default 256 KiB) whose nonces derive from the object nonce plus chunk counter and whose associated data binds repository UUID, object path, DEK version, chunk index, and plaintext length. Chunking keeps SlateDB ranged reads efficient — a range request maps to the covering ciphertext chunks instead of forcing a whole-SST download — and the associated-data binding rejects truncation, chunk reordering, cross-repository object copies, and header or algorithm downgrades as authentication failures surfaced as `data_loss`, never as `not found`.

In key-in-DB mode the repository master key (the same JSON `cat masterkey` prints) is stored in a `meta:` record inside the encrypted database, and vaultic opens the data repository through the existing direct master-key path after the daemon unlocks: one unlock opens metadata and data. Classic password keyfiles remain valid in parallel. Independently, wrapped escrow copies of the master key are stored with one or more cloud vault providers and mirrored into the repository backend, so if the metadata database is ever corrupted beyond repair the escrowed master key alone recovers direct read access to the restic/rustic-format data repository and the legacy JSON rollback path.

**Implementation steps:**

1. Implement `EncryptedObjectStore` in the `vaulticdb` Rust crate wrapping any inner `ObjectStore` (local, S3, and Phase 19's `ReplicatedObjectStore`, so ciphertext is replicated identically to all providers): chunked AES-256-GCM with the header, nonce derivation, and associated-data binding above; exact plaintext-range to ciphertext-chunk translation for `get_range`; strict fail-closed decode rejecting authentication failures, truncation, reordering, foreign-repository objects, nonce reuse, unknown DEK versions, and downgraded headers.
2. Implement the key hierarchy: per-repository random 256-bit metadata DEK generated at initialization, unwrapped once at startup, never persisted or logged in plaintext, held with best-effort locked memory and disabled core dumps.
3. Implement the versioned multi-slot key envelope with atomic new-version publication beside the database and a mirror in the repository backend; implement Azure Key Vault/Managed HSM, AWS KMS (with encryption context), Google Cloud KMS, Vault Transit, and PKCS#11 KEK slot providers behind one wrap/unwrap interface with mockable clients.
4. Implement the offline local recovery slot (Argon2id passphrase KEK with stored salt/parameters, or OS keystore/TPM/PKCS#11 key) so repositories are fully usable for testing and production before any cloud slot exists; adding or removing slots only rewraps the DEK.
5. Implement the unlock policy: slots tried in configured priority order, explicit `--recovery-unlock` acknowledgement plus high-severity `auth` syslog event when a lower-priority recovery slot unlocks a repository that has cloud slots configured, and fail-closed refusal to open a repository whose persistent `meta:encryption` policy requires encryption when no slot can unwrap.
6. Implement key-in-DB mode: store the repository master key in a `meta:` record inside the encrypted database, open the data repository via the existing master-key path when the daemon unlocks, and keep password keyfiles as a supported parallel unlock; never write the master key to logs, environment, or command lines.
7. Implement master-key escrow: wrap copies of the repository master key under one or more cloud vault KEKs with escrow-specific purpose binding, store the escrow records in the repository backend (and optionally the provider secret store), and provide a documented recovery command that retrieves an escrowed key and opens the restic-format repository directly after total metadata loss.
8. Implement rotation: KEK rotation rewraps the DEK without any data rewrite; DEK rotation adds a new DEK version, switches new writes to it, rewrites live objects in bounded checkpointed background batches keyed by each object's header DEK version, verifies zero old-version objects remain, and only then retires the old version; the same rewrap flow rotates escrowed master-key wrappings.
9. Implement migration and policy pinning: `vaultic index encrypt` initializes the envelope and rewrites an existing plaintext database in bounded batches with crash-resumable checkpoints; the persistent `meta:encryption` policy pins algorithm, format version, and required slots so plaintext substitution or downgrade is detected; `index check` validates envelope integrity and slot metadata (without unwrapping), per-object header/DEK-version consistency, and policy pinning.
10. Implement CLI and observability: `vaultic index keys status|add-slot|remove-slot|rotate-kek|rotate-dek|escrow` with stable JSON; `auth` syslog events for unwrap, recovery-slot use, rotation, and failed unwrap attempts; `integrity` events for object authentication failures; log only key identifiers and versions, never key material or wrapped blobs.

**Tests:** encrypt/decrypt round-trip and ranged-read equivalence against a plaintext `ObjectStore` across chunk boundaries and empty/oversized objects; tamper tests (bit flips, truncation, chunk reorder, cross-repository copy, header downgrade, wrong DEK version, nonce reuse) all failing closed as `data_loss` with `integrity` events; envelope tests with mocked Azure/AWS/GCP wrap APIs verifying any single slot unlocks, slot add/remove/rewrap, and atomic envelope versioning; recovery-slot Argon2id unlock, cloud-precedence acknowledgement, and no-silent-downgrade tests; KEK and DEK rotation tests verifying mixed-version reads during rewrite and zero old-version objects afterward; plaintext-to-encrypted migration with crash/resume; key-in-DB open test and escrow recovery test opening the data repository with only the escrowed master key after simulated metadata destruction; fail-closed tests for plaintext substitution, missing envelopes, and all-slots-failing; syslog `auth`/`integrity` routing tests.

**Exit criterion:** every SlateDB object at rest is authenticated-encrypted with a per-repository key that never touches disk in plaintext; the DEK unlocks through any configured slot across Azure Key Vault, AWS KMS, and Google Cloud KMS plus an offline recovery key usable before or without cloud provisioning; one startup unlock opens the metadata database and, in key-in-DB mode, the data repository; the escrowed master key alone suffices to read the restic-format repository after total metadata loss; KEKs and the DEK rotate online without downtime; encrypted repositories refuse plaintext or downgraded operation; and unwrap, recovery, rotation, and authentication-failure events are auditable through the Phase 17 syslog exporter. This closes the metadata-at-rest encryption gaps recorded in the GDPR (Art. 32), ISO/IEC 27001 (A.8.24), and NIS2 (Art. 21(2)(h)) assessments.

**Phase 20 supersession:** Phase 18 key-in-DB and standalone master-key escrow are the migration baseline, not the final custody model. Phase 20 moves the repository master key out of SlateDB and replaces both mechanisms with one pre-database envelope/recovery capsule containing separately wrapped metadata and repository keys under a unified configurable unlock policy.

### Phase 20: Quorum-based encryption unlock (threshold key custody with offline, hardware, and cloud principals)

**Goal:** replace Phase 18 key-in-DB and independently protected master-key escrow with one pre-database, immutable envelope/recovery capsule that contains authenticated wrapped copies of both the SlateDB metadata DEK and the repository data master key. Protect that capsule with explicit, configurable unlock policies ranging from a single offline bootstrap key to cryptographically enforced $K$-of-$N$ groups and composed expressions containing any supported combination of offline keys, YubiKey-backed local hardware seats, and cloud KMS/HSM keys authorized to individual or group-managed principals: Azure Key Vault / Managed HSM with Entra users or groups, AWS KMS or CloudHSM-backed keys with IAM / IAM Identity Center principals, and Google Cloud KMS or Cloud HSM keys with Google Cloud IAM principals or groups. A small, hardened, long-lived key broker owns the unlock ceremony and supplies separately authorized, scoped key leases to `vaulticdb` and transient `vaultic` jobs, so application restarts and controlled software updates do not require another quorum while loss or restart of the broker or host does. A successful configured unlock must recover the data repository even when SlateDB is missing or cannot initialize, while complete operator documentation covers setup, migration, custody, policy changes, application updates, broker lifecycle, and disaster recovery.

**Design:**

A versioned envelope/recovery capsule is stored outside SlateDB at a deterministic bootstrap location beside the database object store, mirrored into the repository backend, and exportable as ciphertext for offline custody. It is readable before SlateDB starts and is the sole managed authoritative copy of two secrets: the metadata DEK used by `EncryptedObjectStore` and the repository master key used to authenticate and decrypt data packs. The repository master key is no longer stored in a SlateDB `meta:` record. Quorum-compliant mode removes ordinary repository password keyfiles, standalone single-provider master-key escrow, and unattended `--key`, `--key-file`, or `--key-command` paths; explicit emergency export remains a non-compliant, high-severity audited action because any plaintext master-key copy bypasses the configured quorum.

The quorum ceremony unlocks a dedicated `vaultic-key-broker`, not `vaulticdb` or a crawl process. The broker is the only component that reads and unwraps the capsule, reconstructs its root secret, and holds both recovered keys between client lifetimes. It starts locked, remains resident across authorized `vaulticdb` and `vaultic` restarts or upgrades, and defines one unlock epoch ending on explicit lock, broker exit or crash, host shutdown or reboot, capsule-policy activation that requires relock, or an optional configured maximum unlocked lifetime. It never persists unwrapped keys or warm-restart material. Consequently, a quorum-compliant deployment has no unattended **broker** startup path, but restarting an authorized application client while the same broker unlock epoch remains active does not require a new ceremony.

Clients use local-only authenticated IPC and receive least-privilege leases rather than capsule access. `vaulticdb` may obtain only the metadata DEK, bound to its authenticated process connection and reacquirable after its restart; a `vaultic` crawl or recovery job may obtain only the repository master key, or a narrower derived capability where the repository format permits it, under a short-lived job lease. The initial implementation releases key bytes into the authorized client's protected memory for compatibility and throughput; making the broker perform bulk pack or object cryptography is an optional stronger mode, not required for Phase 20, because it would substantially expand the broker API and hot-path IPC. Lease expiry limits duration and scope but cannot stop a compromised authorized client from copying a key while leased.

The broker is the central post-unlock trust boundary and must remain substantially smaller than either client. Its IPC authenticates OS peer credentials and an approved component identity, checks executable ownership and a non-writable installation path, and verifies a signed release or deployment identity with component name, allowed-version, and anti-downgrade policy so controlled client updates do not silently broaden authorization. Authorization is never based only on a mutable path, Unix account, caller-supplied name, or executable hash that cannot support controlled replacement. The service runs as a dedicated least-privilege account with local socket ACLs and platform sandboxing, locks secret memory where supported, excludes it from core dumps and diagnostic capture, avoids secret-bearing environment variables, command lines, inherited descriptors, and logs, and zeroizes keys, shares, and leases on release or shutdown. Root, kernel, debugger, broker, or authorized-client compromise during an unlock epoch can extract or use the corresponding keys; quorum protects cold state and creation of a new unlock epoch, not a fully compromised running host.

Each capsule is encrypted under a random per-generation root wrapping secret. Independent wrapping keys are derived with HKDF using the repository UUID, capsule format and generation, root-key version, and distinct purposes (`metadata-dek` and `repository-master-key`), then used with authenticated encryption to wrap the two secrets separately. This domain separation prevents one wrapped payload or implementation path from being substituted for the other. The complete capsule header and both ciphertexts are authenticated and bind repository UUID, envelope generation, algorithms, key versions, unlock-policy hash, and the canonical logical capsule identifier — deliberately not the physical storage location, so the local copy, repository mirror, and offline export of one generation authenticate identically. The authenticated policy also pins the public half of a long-term broker identity keypair used to sign unlock sessions. Unlock succeeds only if both payloads authenticate; partial recovery must never grant either client lease.

An unlock policy is an explicit expression of alternatives and requirements, using `any_of`, `all_of`, and threshold groups. An alternative may be a single offline bootstrap member, a threshold group, or a composed policy such as `(1-of-2 YubiKeys) AND (one separate offline password)`. A threshold group protects the capsule root secret with Shamir secret sharing from a reviewed implementation over a suitable finite field: the root secret is split into $N$ shares with reconstruction threshold $K$, and each share is wrapped independently under one member's protection. Offline members protect a share with an Argon2id-derived KEK from a per-custodian passphrase or with a keyfile on removable media. Hardware members protect a share with a non-exportable key or hardware-derived secret on one or more YubiKeys; the intended personal pattern is a hardware seat where either of two enrolled YubiKeys may unwrap the same member share, combined with a separate password/offline seat so neither the password nor one YubiKey is sufficient alone. Cloud members protect a share with a dedicated versioned cloud KMS/HSM key: Azure Key Vault / Managed HSM through `wrapKey`/`unwrapKey`, AWS KMS through `Decrypt` with an encryption context or AWS CloudHSM-backed key material exposed through an approved wrap/unwrap adapter, and Google Cloud KMS / Cloud HSM through `decrypt` with purpose-bound AAD. Provider IAM scopes each key to one quorum principal or duty group (Entra, AWS IAM / IAM Identity Center, or Google Cloud IAM), while the broker's standing identity can unwrap no cloud share. Each share binds the repository, capsule generation, policy and group IDs, share index, threshold, share count, root-key version, member ID, provider, and key reference, so shares from different repositories, generations, policies, or resharings cannot be combined.

Policies support one or many alternatives such as normal `2-of-4` cloud custodians, break-glass `2-of-3` offline custodians, and personal or small-office policies like `all_of(any_of(yubikey-primary, yubikey-backup), offline-password)`. Every membership, threshold, member-key rotation, or policy change requires an already unlocked broker, generates a fresh root wrapping secret and fresh shares, rewraps both capsule payloads, and publishes and mirrors a new immutable generation without changing either underlying secret. Status reports the minimum effective threshold across every current access path; a retained 1-of-1 bootstrap member, password keyfile, direct master-key copy, single-key escrow, overlapping cloud-principal authorization, duplicate hardware-seat enrollment, or other complete-key bypass makes the repository non-compliant and must never be presented as four-eyes protected. Seat separation is verifiable only for cloud members whose contributions carry validated immutable principal identifiers from Entra, AWS IAM / IAM Identity Center, or Google Cloud IAM. YubiKey-backed seats are hardware-presence verified by pinned public key, serial number where available, attestation where configured, PIN policy, and touch/user-presence proof, but they are not a distinct-human guarantee unless paired with an independent authenticated principal. Offline seats have no verifiable holder identity, so one person holding two offline shares defeats an offline quorum undetectably. Effective-threshold output therefore labels cloud groups as principal-verified, YubiKey seats as hardware-verified, and offline groups as custody-assumed, with human separation enforced by the documented custody runbook. A quorum-compliant repository consequently has no unattended broker startup path: every broker or host restart blocks in the locked state until a quorum completes, persisted warm-restart unlock material is a bypass and is prohibited, and the documentation must state these on-call expectations explicitly. Authorized client restarts and updates reuse only newly authenticated leases from the live broker and never receive persisted broker state.

Because a locked broker cannot call custodian-scoped cloud keys itself or operate a local YubiKey without the operator's PIN/touch ceremony, unlock uses an interactive contribution session. Capsule ciphertext is deliberately non-secret and widely replicated, so the primary residual attack is a fake locked broker phishing custodians for shares; sessions are therefore authenticated, not merely encrypted. The broker reads the capsule without opening SlateDB and creates a one-time session using an authenticated, reviewed HPKE construction with a fresh ephemeral key, nonce, transcript, and expiry, signed by the broker identity key pinned in the capsule policy. `vaultic index unlock contribute` verifies that signature against the capsule, displays a short session fingerprint for out-of-band confirmation between custodians, and embeds in the signed transcript the capsule generation the custodian's tooling last observed. Each custodian authenticates directly with the relevant cloud identity plane (Entra, AWS IAM / IAM Identity Center, or Google Cloud IAM), performs the YubiKey PIN/touch operation, or opens an offline share locally, unwraps only their member share, encrypts it to the verified session, submits it, and zeroizes local plaintext. YubiKey support may use PIV private-key unwrap/key agreement or FIDO2 `hmac-secret`/PRF, but the resulting construction must keep the private key or PRF seed non-exportable, pin the enrolled credential/public key, bind the relying-party or certificate identity to the repository and member ID, and never treat a certificate signature as sufficient unless it gates the encrypted share. The broker validates cloud tenant/account/project boundaries and immutable principal identifiers where applicable and rejects unsigned or wrongly signed sessions, duplicate share indexes, duplicate contributing principals, duplicate hardware-seat contributions, foreign transcripts, expired or replayed contributions, and contributions for another repository or generation. After the policy expression is satisfied it reconstructs the root secret in locked memory, authenticates and unwraps both the metadata DEK and repository master key, zeroizes all intermediate material, permanently closes the session, and begins a new unlock epoch. Because the identity private key necessarily rests in plaintext on the broker host, this raises share harvesting from "anyone holding public capsule ciphertext" to "an attacker controlling the broker host who still deceives the configured quorum"; the fingerprint ceremony and custodian generation checks address that remainder.

The recovered repository master key is available independently of SlateDB health. If metadata opens, normal operation continues with both keys held only in protected broker memory except while copied into an authorized active lease. If SlateDB is absent, corrupt, or fails authentication, an explicitly authorized Vaultic recovery job can lease the already recovered repository master key to enter read-only metadata-loss recovery, inspect or restore packs through the legacy index, and rebuild metadata without writing a plaintext key file. Loss of the broker host also loses the identity private key, so disaster recovery must not deadlock on session verification: contributing to an unsigned session requires an explicit per-custodian `--unverified-session` acknowledgement, mandatory fingerprint confirmation, and a high-severity `auth` event, and the first post-recovery capsule generation pins a fresh identity key. Use of an alternative marked recovery/break-glass requires explicit acknowledgement and emits a high-severity `auth` event. Capsule ciphertext is not secret without a quorum and is replicated aggressively, but loss of every capsule copy is unrecoverable even if all custodians retain their shares.

Ordinary policy changes are online custody operations and do not re-encrypt SlateDB objects or data packs. They do not, however, revoke an old capsule generation already copied together with enough old member credentials. Rollback protection must not rest solely on storage an attacker can rewrite: after total local loss the broker learns the "current" generation from that same storage, making a served old capsule indistinguishable to the broker from legitimate recovery. The custodians are therefore the rollback trust root — contributor tooling caches the last generation it participated in or observed, every signed contribution states that generation, and the broker refuses to complete a quorum whose contributions attest a newer generation than the capsule being unlocked, so a rollback additionally requires deceiving $K$ custodians rather than only the broker. External generation anchors (repository mirror, offline exports, syslog trail) remain supporting evidence. Retiring a historical 1-of-1 metadata path with cryptographic assurance requires metadata-DEK rotation and authenticated object rewrite after that path is removed; suspected exposure of the repository master key requires repository rekeying or pack rewrite and cannot be repaired by resharing alone.

### Phase 22: Operational resilience with relinquishable metadata writers and deferred crawl commit

**Goal:** keep backup data moving through transient metadata-writer contention, VaulticDB maintenance, and complete VaulticDB unavailability. Allow an idle or operator-directed `vaulticdb` instance to relinquish SlateDB writer ownership and remain available as a non-fencing reader, then reacquire writer ownership when required. Allow `vaultic` crawls to encrypt, upload, and verify data packs when VaulticDB is read-only, unavailable, or corrupt by publishing a self-contained authenticated staging journal to the data-pack backends and committing its metadata later. Clearly distinguish durable staged data from a completed, normally restorable backup; never weaken single-writer fencing, snapshot publication ordering, quorum placement, or deletion safety to improve availability.

**Design:**

VaulticDB has an explicit lifecycle state machine: `read-only`, `promoting`, `read-write`, `demoting`, and `fenced`. Read-only instances use SlateDB `DbReader` in a non-fencing mode that follows the latest manifest and WAL without creating managed checkpoints; `SkipWalReplay` is prohibited where current metadata is required. At most one instance owns a writable `Db` for a repository and metadata endpoint. Opening or promoting a writer must acquire a fresh SlateDB fencing epoch through one authoritative strongly consistent coordination/object-store path; metadata replication may copy fenced results but must never elect independent writers from different replicas during a partition. A fenced instance rejects every new mutation, aborts or reports ambiguous in-flight operations without replaying them blindly, closes its writer, and reopens as a reader only after observing the winning epoch.

Automatic demotion is optional and disabled by default. In HA mode, a configurable idle grace period and minimum writer tenure prevent role thrashing; an authenticated administrative command can request immediate demotion. Client connection count alone never proves idleness. Before relinquishing ownership, VaulticDB enters `demoting`, rejects new transactions and write batches with a retryable role-transition response, waits for admitted write RPCs and durable acknowledgements, resolves or expires every transaction, stops metadata maintenance that may write, flushes and durably closes the writable `Db`, and only then reports `read-only`. Timeout or close failure leaves the instance non-promotable and fails closed rather than advertising that ownership was released. Promotion serializes concurrent requests, obtains a new fencing epoch, reopens the latest writable state, validates repository/schema/encryption generations, and requires each caller to revalidate its write intent. Requests carry durable idempotency keys; an ambiguous result is queried by key before retry and is never assumed absent.

Vaultic crawl supports three progressively degraded modes. In `read-write` mode it follows the normal transactional metadata and snapshot publication path. In `read-only-assisted` mode it may use a refreshing reader for prior-snapshot lookup and best-effort deduplication, but treats all observations as stale hints and uploads harmless duplicate blobs rather than relying on freshness. In `data-plane-only` mode it does not open or trust VaulticDB at all, including when metadata is absent, fails authentication, or is operationally unreachable; it performs a full source crawl unless an independent, fully verified `pathdiff` coverage proof safely narrows the scan, builds and encrypts packs locally, and interacts only with configured data-pack backends plus the local Phase 20 key broker. A corrupt VaulticDB is never repaired, overwritten, or used as a basis implicitly by a staging crawl.

Deferred crawls publish an immutable, versioned ingest journal under a repository-scoped staging namespace that compatible Restic/Rustic clients ignore. The journal is independently usable without SlateDB and contains all information needed for deterministic later commit: repository UUID; format, capsule/key, chunker, compression, and placement-policy versions; random job and idempotency IDs; crawl source identity and consistency evidence; the observed basis snapshot and metadata generation when available; encrypted pack IDs, types, sizes, blob IDs, offsets, lengths, compression metadata, and verified backend placements; tree and prospective snapshot records; required inode/path revisions and crawl debt; and hashes linking ordered journal segments to one final seal record. Journal objects are encrypted and authenticated with a purpose-separated staging key derived through the repository key hierarchy, bind every segment to repository/job/sequence/version, and are written with create-only semantics. No plaintext path, file metadata, pack key, share, or broker secret is exposed by staging objects or logs.

Pack upload and journal publication use an explicit state machine: `uploading` → `sealed-pending` → `committing` → `committed`, with `abandoned` and `expired` terminal cleanup paths. A journal becomes `sealed-pending` only after every referenced pack satisfies the configured $K$-of-$M$ durability and failure-domain predicate, each object has been size/hash verified, all immutable journal segments are durable on the required staging backends, and a final authenticated seal commits their ordered hashes. Incomplete or unsealed journals convey no backup durability guarantee and protect no packs indefinitely. A sealed journal is a temporary GC reachability root until its authenticated expiry, successful commit, or explicit abandonment followed by a safety delay and authoritative recheck.

The CLI and API report staged durability separately from repository commitment. A crawl may return a distinct successful-but-pending result such as `data_durable_metadata_pending`, including job ID, protected bytes, placement result, expiry, and why metadata was deferred. It must not publish the normal snapshot object, emit an ordinary backup-success notification, advance an incremental basis, satisfy a backup-completion SLO, or claim normal restorability before metadata reconciliation commits. An emergency restore tool may consume a sealed journal directly after authenticating it and verifying packs, but this is an explicit degraded recovery path and does not turn the journal into an authoritative snapshot prematurely.

When a writer becomes available, a reconciler discovers sealed journals from all staging backends, authenticates and de-duplicates them by repository/job ID, verifies the complete segment chain and seal, rechecks required pack placements and hashes, and rereads current metadata. It resolves concurrent blob locations additively, derives reference counts and mutable aggregates from current authoritative state rather than trusting stale precomputed values, applies deterministic creation/basis conflict rules, and commits packs, placements, blobs, trees, inode/path revisions, crawl debt, analytics inputs, and snapshot authority in one idempotent logical operation. The normal snapshot is published only after all referenced packs and authoritative metadata are durable. An immutable completion record binds the journal hash to the committed metadata transaction and snapshot ID; a crash after database commit but before completion publication is recovered by querying the idempotency ID, not by duplicating changes. Journals whose source-consistency or basis contract cannot be reconciled remain pending or are explicitly rejected, never silently rebased.

Prune, GC, placement eviction, and orphan cleanup enumerate sealed unexpired staging journals before making deletion decisions. They must not delete a referenced staged pack, must not count staged references as committed repository references, and must recheck both journal state and authoritative metadata immediately before deletion. Expiry does not directly delete data: it makes a journal eligible for an audited abandonment flow followed by a configurable grace period, placement revalidation, and idempotency lookup. Staging quotas bound bytes, jobs, age, and per-principal concurrency so an unavailable metadata plane cannot exhaust the data backends; crossing a hard quota stops new uploads before durability is claimed. Administrators can inspect, reconcile, extend within policy, abandon, and garbage-collect jobs, with high-severity acknowledgement for abandoning a sealed journal.

The Phase 20 broker grants a transient crawl only the repository-key capability needed to encrypt packs and derive the purpose-separated staging-journal key. Read-only VaulticDB instances obtain only metadata-DEK leases. Writer role transitions do not require a new quorum while the local broker unlock epoch remains active, but another host needs its own authorized and unlocked broker; this phase does not introduce remote key release. Data-plane-only mode therefore tolerates total VaulticDB loss but not loss of every capsule, an unavailable locked broker, unavailable pack backends, or failure to meet the configured placement quorum.
