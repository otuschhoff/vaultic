# NIS2 (Directive (EU) 2022/2555) Compliance Assessment: Vaultic & VaulticDB

[← Back to compliance index](00-overview.md)

## 1. Executive Summary

This document evaluates **vaultic** and its native metadata daemon **`vaulticdb`**
against the technical and organizational risk-management measures required by
the **NIS2 Directive (EU) 2022/2555**, Article 21(2), and the incident-reporting
obligations of Article 23. Unlike a single-tenant SaaS product, vaultic is a
**component** that essential and important entities (as scoped by NIS2 Annex I/II
and national transposition law) deploy to satisfy their own backup, cryptography,
logging, and supply-chain obligations. This assessment therefore covers both:

1. Vaultic's own security posture as a software supply-chain component
   (build provenance, dependency hygiene, vulnerability handling).
2. The technical capabilities vaultic provides so that an operator can satisfy
   their Article 21(2) obligations for backup/business continuity,
   cryptography, logging, and access control.

NIS2 does not certify products; only competent authorities assess in-scope
entities. This document supports that entity-level assessment by mapping
Article 21(2) measures to concrete, verifiable vaultic/vaulticdb capabilities,
in the same style as the [ISO/IEC 27001:2022 assessment](02-iso27001.md), whose
Annex A controls substantially overlap with Article 21(2).

## 2. Detailed Article 21(2) Measure Analysis

### 2.1 (a) Risk Analysis & Information Security Policy — Rating: 4.3 / 5.0

#### Fulfilled Requirements
- The [architecture documentation](../02-architecture/00-overview.md) makes
  every trust boundary explicit: the vaulticdb process boundary, the
  legacy/authoritative engine resolution, and the non-negotiable guarantees
  that a failed SlateDB open never silently masks corruption or split-brain.
- The [Known Constraints](../04-roadmap/04-known-constraints.md) document
  gives operators an explicit residual-risk register rather than an implied
  one.

#### Residual Gap
- Vaultic ships design documentation but not a turnkey ISMS; the operator
  must still adopt and maintain their own risk-treatment plan referencing
  this documentation as an input (see Section 3, SOP 1).

---

### 2.2 (b) Incident Handling — Rating: 4.6 / 5.0

#### Fulfilled Requirements
- **Multi-Target Syslog Exporter:** Routes categorized (`auth`, `integrity`,
  `gdpr`, `restore`, `lifecycle`) structured events over UDP, TCP, or
  syslog-over-TLS (RFC 5424 / RFC 3164) to a SIEM such as Microsoft Sentinel,
  giving an operator the detection signal Article 23 early-warning timelines
  depend on.
- **Append-Only Lifecycle Log:** Every pack state transition (`created`,
  `published`, `repacked`, `delete_pending`, `deleted`) is recorded in the
  `ph:` event log, providing a forensic timeline for incident reconstruction.
- **Differential Integrity Checks:** `vaultic check --check-hot-cold` and
  `vaultic index check` detect divergence between tiers or corruption of the
  authoritative index, which is the trigger condition for many
  ransomware/tampering incident classifications.

#### Residual Gap
- Vaultic does not itself file the Article 23 CSIRT/competent-authority
  notification; it supplies the detection and evidence trail an operator's
  incident-response process consumes (see Section 3, SOP 2).

---

### 2.3 (c) Business Continuity, Backup Management, Disaster Recovery — Rating: 5.0 / 5.0

#### Fulfilled Requirements
- **Zero Vendor Lock-in:** Repositories remain standard Restic/Rustic format;
  restore is possible with the open-source `restic`/`rustic` binaries even if
  vaultic and vaulticdb are both unavailable (see the
  [competitive analysis](../01-strategy/02-competitive-analysis.md), §3.4).
- **Legacy JSON Fallback:** A SlateDB/vaulticdb outage does not block
  recovery; vaultic falls back to reading the legacy JSON index directly from
  the backend.
- **Multi-Tier Replication:** Hot (NFS/S3 Warm) and cold (S3 Glacier Deep
  Archive) tiers are independently durable, and `vaulticdb` metadata can be
  synchronously replicated across multi-provider cold storage (Phase 19).
- **Retention & Immutability:** Deletion queues (`dq:`) combine with S3 Object
  Lock (Compliance Mode) so a compromised operator credential cannot
  immediately destroy recoverable backup history.

This is vaultic's core value proposition for Article 21(2)(c) and is rated
at full maturity.

---

### 2.4 (d) Supply Chain Security — Rating: 3.6 / 5.0 (Gap)

#### Fulfilled Requirements
- **Pinned Dependencies:** The SlateDB release/commit, Rust target triple,
  and binding checksum are recorded in daemon build metadata (see
  [VaulticDB Service Architecture](../02-architecture/01-vaulticdb-service.md),
  §2, Build requirements).
- **Static, Reproducible Builds:** `vaulticdb` is built statically for Linux
  with the musl target, avoiding dynamic-linking supply-chain drift at
  runtime.
- **No Generated-Code Drift:** Generated protobuf/UniFFI files are updated
  only by a pinned regeneration workflow; hand-written code must not edit
  generated files.

#### Residual Gap
- There is no published Software Bill of Materials (SBOM) or automated
  dependency-vulnerability scan gate in the current roadmap. Until this
  lands, an operator must run their own SBOM/SCA tooling against vaultic's
  `go.mod`/`Cargo.lock` as a compensating control (see Section 3, SOP 3).
  Tracked as a roadmap gap; not yet assigned to a phase.

---

### 2.5 (e) Security in Acquisition, Development, Maintenance & Vulnerability Handling — Rating: 3.8 / 5.0 (Gap)

#### Fulfilled Requirements
- **Staged Rollout:** All behavior-changing work ships behind feature flags
  (`Alpha` → `Beta` → `Stable`) per the
  [rustic-parity guiding principles](../01-strategy/01-vision-and-principles.md#part-b--rustic-feature-parity),
  bounding the blast radius of a defective change before it reaches default
  behavior.
- **Phased, Exit-Criteria-Gated Development:** Every roadmap phase in
  [04-roadmap/](../04-roadmap/00-overview.md) has explicit tests and exit
  criteria before being marked complete, rather than shipping unverified.

#### Residual Gap
- There is no publicly documented coordinated vulnerability disclosure (CVD)
  policy or security contact for vaultic itself. An operator relying on
  vaultic for a NIS2-in-scope service should establish their own vulnerability
  intake process that covers vaultic as a dependency until an upstream CVD
  policy is published (see Section 3, SOP 3).

---

### 2.6 (f) Policies to Assess Effectiveness of Security Measures — Rating: 4.5 / 5.0

#### Fulfilled Requirements
- **Continuous Verification:** `vaultic index check`, `vaultic check
  --check-hot-cold`, and sampled storage verification (Level 1/2/3, see
  [Security & Verification Architecture](08-security-and-verification-architecture.md))
  give an operator a repeatable, schedulable control-effectiveness test
  rather than a one-time audit.
- **Reference Feasibility Profiles:** The analytics/placement roadmap phases
  define explicit benchmark gates (storage overhead, reconciliation CPU
  overhead, query latency) that must pass before a feature is enabled by
  default, which doubles as a change-effectiveness review.

---

### 2.7 (g) Basic Cyber Hygiene & Security Training — Rating: 3.0 / 5.0 (Operator-Dependent)

Cyber hygiene and staff training are organizational controls that a backup
tool cannot itself enforce. Vaultic's contribution is limited to reducing the
opportunity for hygiene failures to cause data loss (encryption-by-default,
no unencrypted repositories, explicit `--confirm` gates on destructive GDPR
erasure operations). The remainder of this measure is entirely the operator's
responsibility (see Section 3, SOP 4).

---

### 2.8 (h) Cryptography and Encryption Policy — Rating: 5.0 / 5.0

#### Fulfilled Requirements
- **Client-Side Zero-Knowledge Encryption:** Identical technical control to
  [ISO 27001 Control A.8.24](02-iso27001.md#21-cryptography-control-a824--rating-50--50):
  AES-256-CTR with Poly1305/HMAC-SHA256 authenticated encryption, Argon2id/
  Scrypt key derivation, and Azure Key Vault Option A passphrase fetching via
  Azure Arc Managed Identity.
- This is a single control shared verbatim between the ISO 27001 and NIS2
  assessments; see the ISO 27001 document for full technical detail.

---

### 2.9 (i) Human Resources Security, Access Control & Asset Management — Rating: 4.0 / 5.0

#### Fulfilled Requirements
- **Access Control:** `vaulticdb` defaults to Unix domain sockets (`0700`
  directory, `0600` socket); an opt-in TCP listener requires a non-empty IP
  allowlist and authenticated channel, or it refuses to start.
- **Asset Management:** The backend registry, pack catalog (`p:`), and
  backend-pack index (`bp:`) give an operator a queryable inventory of every
  physical storage asset and its placement, satisfying the asset-management
  half of this measure.

#### Residual Gap
- Human resources security (personnel vetting, role changes, offboarding) is
  entirely an operator organizational control; vaultic has no user-identity
  concept beyond the repository key and optional TCP authentication token.

---

### 2.10 (j) MFA / Continuous Authentication & Secured Communications — Rating: 3.7 / 5.0 (Gap)

#### Fulfilled Requirements
- **Secret Retrieval:** Azure Key Vault Option A uses Azure Arc Managed
  Identity, which is itself a strongly-authenticated, non-interactive
  credential flow.
- **Secured Channels:** Optional TCP transport requires mutual TLS and an IP
  allowlist; the multi-target syslog exporter supports syslog-over-TLS.

#### Residual Gap
- There is no multi-factor authentication for interactive CLI/operator
  access to a repository; authentication is a single repository
  passphrase (optionally vaulted) or a TCP bearer token. An operator
  requiring MFA for interactive access must enforce it at the host/bastion
  layer, not within vaultic itself (see Section 3, SOP 5). Tracked as a
  roadmap gap; not yet assigned to a phase.

---

## 3. Operational NIS2 Compliance Guidelines & Standard Operating Procedures (SOPs)

To rely on vaultic as part of a NIS2-compliant risk-management framework:

1. **Risk Register (Art. 21(2)(a)):** Import [Known Constraints](../04-roadmap/04-known-constraints.md)
  and the [Rollout and Rollback](../04-roadmap/03-rollout-and-rollback.md) plan
   into the entity's own risk register as documented residual risks and
   compensating controls.
2. **Incident Response (Art. 21(2)(b), Art. 23):** Wire the multi-target
   syslog exporter's `integrity` and `auth` categories into the entity's
   CSIRT-facing SIEM so the 24-hour early-warning and 72-hour notification
   clocks can start from an automated detection event rather than manual
   discovery.
3. **Supply Chain & Vulnerability Intake (Art. 21(2)(d), (e)):** Until an
   upstream SBOM/CVD policy is published, run independent SCA/SBOM tooling
   against vaultic's `go.mod` and `vaulticdb`'s `Cargo.lock` on every pinned
   version bump, and register vaultic in the entity's own dependency
   vulnerability-intake process.
4. **Cyber Hygiene & Training (Art. 21(2)(g)):** Train operators on the
   destructive-operation confirmation gates (e.g. GDPR
   `execute-forget --confirm`), the meaning of `--dry-run`, and the
   non-negotiable guarantee that legacy JSON indexes are never silently
   deleted.
5. **Access Layer MFA (Art. 21(2)(j)):** Require MFA at the host/bastion or
   jump-box layer for any interactive session that can reach a repository
   passphrase, Azure Key Vault secret, or vaulticdb TCP endpoint; do not rely
   on vaultic to enforce this itself.
